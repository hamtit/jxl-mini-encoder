# 写真向け最適化の検証

## 条件

- ベース: `756ca0a`（origin/main）。各変更は直前の採用済み変更とも比較。
- Core i5-1135G7（4コア/8スレッド）、Linux x86_64、release、通常のランタイムAVX2検出。
- 写真: [Kodakの24枚](https://r0k.us/graphics/kodak/)。画像はリポジトリに同梱しない。
- 時間/RSSの反復比較: kodim01, 03, 06, 08, 13, 18, 21, 23。
- スケーリング用: kodim13をLanczosで3072×2048に拡大。独立した高解像度写真ではなく、メモリ・並列化のストレスケース。
- 各時間/RSS条件は3回。基準と候補を交互に起動し、中央値で比較。
- `eval --encode-only` の内部時間と、GNU timeの最大RSSを使用。RSSには入力読み込み・アロケータ保持領域を含むが、復号とSSIMULACRA2の領域は含まない。
- 画質比較は別プロセス。SSIMULACRA2は小数点以下2桁のeval出力。Butteraugli・主観評価の優位性を保証するものではない。

## 採用した変更

### 1. 逆Gaborishの行バッファ化

全画像サイズの出力平面を確保せず、各バンドの境界行を先に保存し、5行のリングから処理する。行内の演算順序は維持。

6MP・q90/e7/t1のピークRSSは146,704→124,624 KiB（約15%減）、時間は2,094→2,097 msでほぼ不変。t4では後段・アロケータのピークが支配的で、プロセス全体のRSS削減は確認できなかった。

8枚のq75/e7/t1、q90/e7/t1、q95/e7/t4、q90/e9/t1と6MPのt1/t4で出力ハッシュが完全一致。小幅・浅い画像、端数バンド、多スレッドでは従来実装とのビット単位比較も行う。浅い画像はワークスペースが不利になるため従来経路を使う。

### 2. 変換探索の安全な枝刈り

係数コストは非負で、残りの歪みも非負。途中の係数コストだけで比較対象以上になった候補は、逆DCTと画素誤差計算を省略する。未完了の評価は正確なコストとしてキャッシュしない。

直前の変更との写真8枚合計比較:

| 条件 | 前 ms | 後 ms | 変化 |
|---|---:|---:|---:|
| q75/e7/t1 | 1074.9 | 1032.4 | -4.0% |
| q90/e7/t1 | 1161.8 | 1003.3 | -13.6% |
| q95/e7/t4 | 472.1 | 418.2 | -11.4% |
| q90/e9/t1 | 1771.6 | 1465.4 | -17.3% |
| 6MP q90/e7/t1 | 2083.7 | 1915.6 | -8.1% |
| 6MP q90/e7/t4 | 763.9 | 725.6 | -5.0% |

すべて出力ハッシュが一致。RSSは実質不変。テストでは、変動する量子化場・マスクを使って、枝刈りなしの探索とタイル選択・事前評価の利得を比較する。

### 3. 中～低品質域のEPFを弱める

逆Gaborish有効かつdistance >= 1.5のときだけsharpnessを4→3にする。高品質域、逆Gaborish無効時（平坦な図形、低effortなど）の設定は維持。新たな画像サイズの領域は不要。

24枚、ほぼ同じサイズでのSSIMULACRA2差:

| 品質 | 平均差 | 最悪 | 最良 | 合計サイズ差 |
|---|---:|---:|---:|---:|
| 40 | +1.903 | +0.92 | +2.94 | -0.0012% |
| 60 | +0.255 | +0.03 | +0.56 | -0.0005% |
| 75 | +0.113 | -0.05 | +0.34 | -0.0012% |
| 82 | +0.047 | -0.10 | +0.12 | +0.0026% |
| 90 | 0 | 0 | 0 | 0% |
| 95 | 0 | 0 | 0 | 0% |

q90/q95は出力ハッシュも一致。q75の8枚の追加計測では時間1058→1066 ms程度のばらつきがあったが、一貫した速度・メモリ差はなかった。画質改善として採用する。サイズ差は主にsharpnessメタデータの符号化差で、画像のAC係数は変わらない。

## 不採用・保留

- **CfLコストの8レーン加算**: 写真の速度差は-2%～+3%程度で一貫せず。不採用。
- **DCT転置の8×8タイル化**: 出力は一致したが、複数条件で約8～13%遅くなった。不採用。
- **AQ場を一様量子化と半々に混合**: 同サイズの写真8枚で平均SSIMULACRA2がq75で-0.43、q90で-0.28。不採用。
- **EPF sharpnessを全品質で2にする**: q75平均+0.13だが高品質の利得がなく、sharpness 3より安定しない。不採用。
- **逆Gaborishの一律無効化**: 前回の同サイズ比較では画像ごとの良し悪しがあり、恒常的なデフォルト変更には不十分。元の環境変数による切り分けは維持。
- **ANS refillのビットセット＋可変長ワード列**: 単体の作業領域は減るが、非可逆写真の実測ピークRSSはほぼ不変。6MPの可逆で一部削減する一方、速度も悪化した条件があり不採用。
- **選択DCT係数のフレーム全体キャッシュ**: 単純な実装では12バイト/画素を追加し、6MPで約72MiB必要。今回のメモリ方針に合わないため導入しない。グループ単位の処理再編が必要。
- **探索と本量子化の完全な整合・反復誤差フィードバック**: 追加の再構成・探索パスが必要で、速度/メモリとの交換条件が未確立。今回の測定で効果が確認できた変更には含めない。

## デコーダ依存の既知の評価上の制約

`kodim08.png`、q90.38671875/e7/t1、`MINI_NO_GABORISH=1`で、jxl-oxide 0.12（jxl-modular 0.11.3）は`InvalidAnsStream`になる。元のmainの出力でも再現し、同じファイルはFFmpegのlibjxl 0.11.1で正常に復号できる。ANSを元のコンテキスト列で個別に復号した検査も一致した。

jxl-modularの単純テーブル経路が、前チャネルを参照するプロパティのときにも空の前チャネル列を使う点が原因候補。今回は依存デコーダや合法なエンコーダ出力に回避策を入れない。上記24枚×6品質の通常設定の評価は全件復号できた。この条件を含む任意のサイズ探索では、エラーを隠さずlibjxlで別途切り分ける必要がある。

## 再現手順

まず基準リビジョンと候補でそれぞれ `cargo build --release --example eval --locked` を実行し、基準バイナリを別名で保存する。基準にも `--encode-only` 対応のevalを使う（ライブラリ側は基準のまま）。

```sh
python3 tools/compare_photos.py \
  --baseline /path/to/baseline-eval \
  --candidate target/release/examples/eval \
  --quality 40 --quality 60 --quality 75 --quality 90 --quality 95 \
  --threads 1 --threads 4 --runs 3 --match-size \
  --output comparison.json /path/to/kodak/*.png
```

比較ツールはライブラリの同じ品質で時間・RSS・ハッシュを測り、`--match-size` 指定時だけ別途近いサイズを探索して画質を測る。サイズの非単調性に備え、実際のサイズ差と許容誤差内かどうかを結果に残す。復号失敗はそのままエラーにし、成功した途中結果はJSONに保持する。

高解像度の拡大画像は写真24枚の平均画質には含めない。温度や同時実行負荷で数%の時間・RSS差が出るため、小さな差を単独で採用理由にしない。
